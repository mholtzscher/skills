# Refactoring

If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign that changes behavior is allowed, but name it and route to Feature. Large or cross-cutting structural work belongs to [exploration](../exploration/PLAYBOOK.md) and [planning](../planning/PLAYBOOK.md).

Inspect first and propose the behavior contract, executable pin, target shape, migration, and verification through [planning](../planning/PLAYBOOK.md). Wait for sketch/spec approval before writing tests, harnesses, or product changes. Approval does not waive the requirement to execute the pin on the original code before structural edits.

1. **Pin the behavior contract first.** Use [How](../explanation/PLAYBOOK.md#how) over the affected subsystem to learn the contract, then establish an executable characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. Existing adequate executable coverage can serve as the pin; run it against the original and identify the behavior it protects rather than adding meaningless mirror tests. If the area has no coverage, write and execute the approved pin before touching structure. Type check and lint are not a pin. Read [Test behavior](../../principles/test-behavior.md) when choosing or writing the check.
2. **Name the structure the code is missing** per [Model the domain](../../principles/model-the-domain.md). Boring code stays when the shape is already clear and local. Diagnose the branches or invalid states the reshape can delete, rather than adding indirection. Require a concrete reader-burden reduction, not an arbitrary deletion quota: name the rules, states, dependencies, jumps, or coordination work that disappear and where retained responsibilities go. Read [Minimize reader load](../../principles/minimize-reader-load.md); use [show-complexity](../show-complexity/PLAYBOOK.md) when the benefit or retained responsibility is unclear. Keeping the current structure is a valid conclusion.
3. **Name the target shape.** State what the module layout, types, and call graph should be if built today. If the target crosses a function boundary, assess the ownership and caller consequences before the move. Use [exploration](../exploration/PLAYBOOK.md) for consequential or uncertain design choices; an ordinary function boundary does not require a panel. Resolve material target changes through the approved planning path.
4. **Subtract before you add.** Trace production callers and supported external contracts before labeling code obsolete. Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape where those changes preserve the contract. The smallest change that reaches the target shape ships. A speculative cleanup that “might help” gets reverted; revert only your own changes, preserving user work.
5. **Move in small behavior-preserving steps, each keeping the pin green.** For internal API reshapes, migrate every caller in dependency order and delete the old API in the same wave. No throwaway compatibility shims or parallel old-and-new internal paths; preserve genuine supported external compatibility requirements. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. Keep mechanical edits bounded to confirmed file paths, names being moved, and behavior to hold.
6. **Prove behavior is unchanged on the real artifact**, not “it compiles” ([Prove it works](../../principles/prove-it-works.md)). Verify across the affected consumers. For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface via the relevant browser, terminal, or project control tool. Missing tools or unexecuted checks are verification gaps, not equivalence proof.
7. **Confirm the change is worth keeping.** The success measure is reduced reader load. If the diff does not lower reader load somewhere, revert the owned refactoring changes. Describe the actual reduction in rules, indirection, ownership, or operating work, not a line-count score. Preserve user work and report any blocker to safely reverting your changes.
8. **Shape small ordered commits.** A subtraction commit, then the reshape, then any follow-on cleanup. Use [Verifiable units](../../principles/verifiable-units.md), so each behavior-preserving slice stays green before the next. Prefer this order as you work; do not automatically rewrite published or user history. [Finish delivery](../finish-delivery/PLAYBOOK.md) with one ordinary unmerged PR and scoped required-CI repair.

**Reply:** the structure that changed, the pin you held it against (including its original-code run), the equivalence proof, the reader-load delta, what shipped and what got reverted. State verification gaps explicitly.
