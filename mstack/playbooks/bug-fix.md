# Bug fix

Read [Question the premise](../principles/question-the-premise.md).

The lead owns the plan, review, verification, and final evidence. Use direct work or selective bounded delegation through [orchestration](../references/orchestration.md), with actual host-configured roles and models.

Every shipped change must address a mechanism supported by runtime evidence. A precaution that "might help" remains a hypothesis, not a fix. Discard changes motivated by a refuted hypothesis, reverting only your owned, scoped edits. Preserve user work, unrelated changes, history, and diagnostic evidence.

1. **Reproduce the reported failure.** Establish the intended behavior, symptom, trigger, and affected revision. Inspect existing tests, logs, traces, and relevant consumers. Drive the actual matching UI, CLI, or service boundary yourself with available tools and the relevant control skill, such as agent-browser or terminal-control. A debug protocol's request for the user to reproduce is not a reason to skip available control tools. Drive them as far as current authority allows before asking the user, then state the specific reason they cannot reach the target. If the failure does not appear, synthesize the trigger, tighten conditions, or instrument the path within approved scope. New code or a stateful experiment requires [approval](../SKILL.md#scope-and-approval) and an isolated disposable target. Bound the investigation by the task's budget and authority. Missing reproduction evidence leaves the cause unproven rather than making source inspection a substitute.
2. **Eliminate competing hypotheses.** Ground the affected subsystem with [How](explanation.md#how), and use [Why](explanation.md#why) when regression history or design rationale matters. Enumerate candidate causes. Choose the next observation that cuts the most remaining problem space, using binary search where the problem permits it. Run the code and read the logs or traces rather than guessing. After each pass, record what was excluded and what remains. When program state is unclear, obtain instrumentation evidence before speculative fixes or parallel fix proposals. Approval still governs new instrumentation and live evaluation. Confirm the surviving mechanism with runtime evidence before implementing or shipping a fix. If runtime access is unavailable, report the source-supported hypothesis and the missing deciding observation. Iterate while this session is executing, not through imagined unattended wakeups or restart survival.
3. **Plan the smallest supported fix.** Follow [planning](planning.md) and obtain approval of the fix sketch or spec. An approved issue description alone does not approve an implementation shape unless the conversation settled that shape. Crossing a function boundary prompts inspection of coupling and ownership. Use [Architecture](exploration.md#architecture) when consequential design uncertainty warrants it, not for every cross-function edit. Implement directly or delegate a specific scope, and review any delegated diff. No model sheet or model setup is required.
4. **Establish regression evidence before the fix.** Use [focused regression testing](../references/verification.md#focused-regression-testing) when explicitly requested or when a cheap meaningful local test path exists. Preserve the actual failing-before evidence before changing production behavior. If a test is impractical, use the closest authorized executable check and explain its limits. A unit test establishes the behavior it exercises, not the absence of the reported bug.
5. **Fix and verify the mechanism.** Make the smallest production change the evidence justifies, preserving nearby contracts. Rerun the original reproduction on the same real boundary and run material nearby regression checks through [verification](../references/verification.md). An inconclusive result or a different boundary is not a pass. Keep the failing-before and passing-after receipts tied to their revisions and ordered checks. Follow [Verifiable units](../principles/verifiable-units.md) for a coherent test-before-fix story. Separate commits may preserve that sequence inside an already-approved isolated phase, with a green exit before publication. This does not authorize broken shared or published state, automatic rebasing, or rewriting user history.
6. **Finish the approved coding task.** Use [finish delivery](finish-delivery.md) for cleanup, one ordinary unmerged PR, and scoped required-CI repair. Unproven mechanism or missing same-boundary verification remains an explicit completion gap.

In the reply, state what was broken, the root cause, the fix, and how you verified it. Include the actual commands, tested revisions, and critical failing-then-passing reproduction output verbatim. Keep receipts bounded to the relevant evidence. Preserve privacy through permission-scoped redaction and disclose any redaction. Never fabricate output or rerun checks merely to improve the story. If failing-before or passing-after evidence is missing, say why, name the closest check used, and state what remains unproven.
