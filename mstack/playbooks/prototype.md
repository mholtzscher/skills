# Prototype and visual parity

Distinguish a disposable decision experiment from a production change.

## Prototype

For a prototype, define the uncertainty, observable comparison, smallest sketch, output location, and disposal/preservation plan. Get sketch approval before writing code. Build only enough to answer the question. Compare actual results, state what was simulated, and recommend the next decision. A prototype does not automatically publish a PR or authorize production implementation.

## Visual parity

**You own the agreed visual-equivalence contract. Default to pixel-exact equivalence. The baseline is the spec. You do not touch it.** Equivalence is verified by image diff, not by eye. An attractive mock is not parity evidence.

Differences are allowed only when explicitly approved **before comparison**, with predefined exceptions per state, region, or property in the agreed contract. Report those exceptions separately, retain raw diff evidence, and require zero unexplained pixels. Never call a nonzero result pixel-exact. Do not invent post-hoc tolerance, masking, or baseline overwrites to bury failures. A materially revised contract requires user agreement and a new clearly versioned comparison, not a retroactive pass.

1. **Establish the baseline first, before any migration:** a visual regression harness that screenshots the current component across its states, plus the target when matching two implementations. Define the reference screenshot/implementation and state matrix: viewport, data, interaction state, and any explicitly approved differences for each comparison. Preserve those conditions between captures. Propose and approve the harness and implementation shape before writing new harness or migration code; reuse existing approval. Establish the reference, screenshots, and executable harness before product migration. No baseline, no parity claim. A blocking prerequisite, not a follow-up.
2. **Anti-shortcut clauses, stated and held:** keep the harness and baseline immutable through the comparison. No harness modifications, baseline tampering, or unrelated component restructuring to make a diff pass. Legitimate reshaping within the approved migration is allowed; test gaming is not. If the baseline looks wrong, stop and ask, don't edit it. If no credible comparable driver exists, stop the parity claim and ask; do not silently relax the criterion. An approved correction establishes a new clearly versioned comparison and baseline before migration resumes, preserving the old evidence rather than overwriting it into a pass.
3. **Migrate one component at a time.** Shared primitives migrate first as a blocking phase. Keep one owner per component; when independent component writers materially help, isolate them in separate worktrees through [orchestration](../references/orchestration.md) and [Separate ownership](../principles/separate-ownership.md). Give shared primitives an owner and accept that phase before dependent component migrations. Parallelism is selective, not a requirement to create extra writers.
4. **Verify each component against its baseline via image diff on the matching surface**, using an actual available browser, terminal, or project-specific driver. Discover host capabilities through the adapter for [OpenCode](../references/hosts/opencode.md) or [Pi](../references/hosts/pi.md). Use the relevant installed specialist when available; report a missing driver as a verification gap. Capture comparable real screenshots and exercise real interactions to preserve behavior, not only appearance. Under the default contract, a nonzero diff is a fail. Investigate the pixel delta. Under an explicitly approved exception contract, identify the predefined exceptions separately and block on any unexplained difference. Iterate per component while this session is executing until the agreed contract is met; keep the baseline and harness frozen. Unattended wakeups or restart survival require a real scheduler; report the missing capability rather than promising continuation.
5. **Finish approved production delivery** through [finish delivery](finish-delivery.md): one ordinary unmerged PR with per-component evidence and scoped required-CI repair, not automatic per-component or stacked PRs. Preserve the requested scope; a baseline-only investigation or disposable prototype does not authorize production migration or publication.

**Reply:** components migrated, the raw diff result and agreed-contract result for each state/component, separately reported approved exceptions, baseline/harness location and comparison version, interaction verification, and what's left. Report missing drivers, unrun states, and other verification gaps; unexplained differences block completion.
