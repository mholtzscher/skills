# Runtime and trace forensics

The default deliverable is a diagnosis, not a fix.

Permission to diagnose is not permission to alter production data or restart an unrelated service.

Build a causal account with source and measurement evidence, competing hypotheses, and specific gaps. Use [Explain the number](../../principles/explain-the-number.md). End when the diagnosis is supported or the next discriminating observation is named. Route a requested fix through [bug fix](../bug-fix/PLAYBOOK.md) or [performance](../performance/PLAYBOOK.md), retaining the approval boundary.

## Runtime forensics

Diagnose from the live process. Source inspection informs hypotheses but does not replace a captured signal.

1. **Capture the live signal.** Discover the actual control tools and relevant external skills available for the matching UI, CLI, or service boundary. Capture a CPU profile for a spinning process, a heap snapshot for a leak, or a CDP trace for a visual glitch. Use a bounded capture and cite the actual artifact. Record process identity, revision, workload, capture window, tool settings, and observer overhead. Capture authority does not include installing tools, changing configuration, enabling persistent logs, or changing production. If access or authority is missing, name the missing signal instead of inventing an artifact.
2. **Reduce the artifact.** Identify the function on the hot path, the retainer chain from a leaked object to a GC root, or the loop firing without input. Use the [trace procedure](#trace-forensics) for fixed-artifact parsing. For large artifacts, use deterministic queries and, when useful and available, selective bounded delegation through [orchestration](../../references/orchestration.md). Follow [Guard context](../../principles/guard-context.md) by keeping the reduced finding and evidence pointers in the lead's context rather than the raw payload.
3. **Confirm the mechanism.** Choose the smallest observation or experiment that distinguishes the hypothesis from alternatives. CDP evaluation that injects instrumentation into the running process, or a live code hotfix without reloading, can confirm the mechanism cheaply. These are stateful experiments, not read-only inspection. Obtain separate approval for a bounded, reversible experiment, reuse adequate existing approval, and specify the target, permitted effects, restoration, and stop conditions. New code needs the existing sketch/spec gate and an isolated disposable target. Missing access or authority leaves the mechanism a hypothesis. Do not reset state, restart or terminate unrelated processes, or discard the original evidence to force confirmation.
4. **Map the finding to source.** Cite the source file, symbol, and allocation or scheduling line at the matching revision. Distinguish directly observed signal, inferred mechanism, and runtime-confirmed mechanism. If symbols or source mapping are missing, name that gap rather than presenting complete attribution.
5. **Report the actual activity.** Report any authorized instrumentation or live hotfix that changed state.

Reply with the captured signal, reduced finding, mechanism proof or its limits, source location, artifact paths, and the next discriminating observation if needed.

## Trace forensics

Start from the supplied artifact and treat it as a fixed dataset. Do not rerun the workload or capture unless separately requested. Preserve the original bytes. Put permitted derivations in an explicitly approved output location, outside the original artifact.

1. **Identify the format and tool.** Use DevTools or a trace parser for a `.cpuprofile` or `.json.gz`, a text editor for a spindump, and appropriate heap tooling for a `.heapsnapshot`. Establish the capture conditions and missing context before interpreting it. For bulky parsing, use the same selective delegation and reduced-evidence discipline as Runtime forensics.
2. **Reach a queryable form before detailed analysis.** Do not eyeball huge JSON. Use an adequate tool's existing query representation, or transform a large trace or heap snapshot into SQLite with one row per sample, frame, or node. Preserve identifiers, timestamps, units, symbols, edges, and relationships so call trees and retainer paths retain their meaning. A tiny artifact or an already-queryable tool does not require conversion. Creating a parser, database, or other derived artifact needs agreed analysis-write authority. If that authority is absent, propose the smallest useful conversion rather than writing it silently.
3. **Narrow to the mechanism.** Query the frames holding the most time and walk the call tree to the hot path. For a leak, follow the retainer chain from the leaked object to a GC root. For a spindump, identify the thread stuck on-CPU or blocked and its wait reason. Cite the samples, frames, nodes, or query results supporting the reduced finding.
4. **Attribute to source.** Map the relevant frame or node to file, symbol, and line using the artifact's symbols and matching source revision. Resolve missing symbols when possible within authority. A hot frame without source mapping is not a complete attributed diagnosis. Say plainly when the artifact lacks the mapping and what that prevents you from concluding.
5. **Compare paired evidence when available.** Diff before and after captures, checking workload, build, window, and capture-setting equivalence. Name the actual known intervention and possible confounders. A pair with a different workload does not establish causation. State what a comparable pair confirms and what remains inferred. Without a pair, label the finding the strongest hypothesis the artifact supports, not a confirmed cause.
6. **Return the diagnosis.** Cite the artifact and format, capture conditions, reduced finding, source location, artifact and permitted derivation paths, and whether a comparable pair confirmed the finding. State confidence, missing mappings, authority limits, and the next useful observation. End at diagnosis unless a fix was separately requested and approved. Name authorized stateful activity honestly if the task separately included it.
